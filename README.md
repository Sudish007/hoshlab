# Hoshlab · होशलैब

Hoshlab is an **agentic company**: 8 AI agents and 1 human owner (Sudish Kumar) that run the Instagram pages of three real products — [@rishtapatra](https://www.instagram.com/rishtapatra/) (RishtaPatra, biodata · kundali · rishta), [@kaatdo](https://www.instagram.com/kaatdo/) (KaatDo, the kill switch for F&O traders) and [@job_rez](https://www.instagram.com/job_rez/) (JobRez, resume builder). The agents run inside GitHub Actions on a schedule; every idea, draft, approval, run and published post is a JSON, JSONL or Markdown file under `company/`; the public site at https://sudish007.github.io/hoshlab/ is built from those files on every push; the owner steers everything from a browser-only admin at `/admin/` (unlinked, reached by URL).

Plain Node ESM (Node >= 22.2 locally, Node 24 in Actions), no framework, no bundler, no TypeScript, no vendor SDKs. Dependencies are exact-pinned (`marked`, `playwright`, ten `@fontsource/*` packages; `fast-xml-parser` for tests). Media binaries (rendered JPEGs) live on an orphan `media` branch, never on `main`.

The roster (`company/roster.json`): CEO (weekly memo, Mondays) and Writer on Anthropic `claude-sonnet-5-5`; HR (monthly review on the 1st) and QA on Google Gemini `gemini-3.8-flash`; Strategist and Analyst (weekly report, Sundays) on OpenAI `gpt-6-luna`; Designer and Publisher are deterministic code, no language model. Each agent's working rules are a Markdown charter in `company/charters/`, editable in the admin. Each page's facts, pricing, voice, disclaimers, forbidden words and design tokens are a brand charter in `company/brands/`, every fact row pointing at a file and line in the product's own repository.

**Status of this repository at the time of writing:** the code is built and tested offline (`npm test`, the Playwright audits and the end-to-end dry run pass on the owner's machine with mock models and the dry-run Instagram client). Live so far: GitHub Pages serves the site at https://sudish007.github.io/hoshlab/ (HTTP 200 on every page), the `media` branch exists and carries only the fixture samples (`sample: true`, nothing from a real draft), and `engine-daily.yml` and `publisher-hourly.yml` run on their schedules and commit `status.json` and the run log as `hoshlab-bot` — with every page still `not_configured`, so no agent has called a model and no post has been attempted. Still **not configured yet**: the provider keys and the Instagram tokens (the `check-models` and the engine rows say so until `scripts\setup-secrets.ps1` has run). Still **untested**: `token-refresh.yml` (zero runs; nothing to refresh without tokens) and the real Instagram publishing path, until the throwaway post below. The site prints `—` / `No runs yet` in its status strip only until the first engine run; today it lists the bot's runs, whose CEO and Strategist rows failed for want of a provider key.

|---|---|---|

| `GEMINI_API_KEY` | HR, QA (and fallbacks) | aistudio.google.com |
| `OPENAI_API_KEY` | Strategist, Analyst (and fallbacks) | platform.openai.com |
| `IG_TOKEN_RISHTAPATRA` | Publisher, page @rishtapatra | Meta app → API setup with Instagram login |
| `IG_TOKEN_KAATDO` | Publisher, page @kaatdo | same |
| `IG_TOKEN_JOB_REZ` | Publisher, page @job_rez | same |
| `HOSHLAB_SECRETS_PAT` | the weekly token refresh (`gh secret set` needs it; `GITHUB_TOKEN` cannot write secrets) | github.com → Settings → Developer settings → Fine-grained tokens (this repository only, **Secrets: Read and write**) |

The workflows pass them to the engine as environment variables (`env:` blocks in `.github/workflows/engine-daily.yml`, `publisher-hourly.yml` and `token-refresh.yml`); in those workflows `GITHUB_TOKEN` has `contents: write` (plus `actions: read` for the first two) only (the deploy job adds `pages: write` and `id-token: write` for Pages). The admin never holds a provider key, an Instagram token or the PAT — it can approve, edit, move, reject and dispatch workflows, but it cannot post. Logs scrub every secret value; `check-models` prints presence and model ids, never key material.

**Token refresh** (`token-refresh.yml`, Mondays 07:30 IST, cron `0 2 * * 1` UTC, also dispatchable): `node engine/index.js refresh-tokens --commit` reads `company/state/tokens.json` (per page: `username`, `expiresAt`, `refreshedAt`, `state` — never a token) and, for every page whose expiry is **less than 20 days away or not known yet**, calls `GET https://graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token` with the stored token (Meta refreshes a long-lived token that is at least 24 hours old and not yet expired; the new one is valid for 60 days). The new value is piped on standard input to `gh secret set <NAME> --repo Sudish007/hoshlab`, authenticated by `GH_TOKEN` = `HOSHLAB_SECRETS_PAT`; it never appears in a command line, a log or a file. `tokens.json` then records the new expiry (`now + expires_in`) and `status.json` mirrors it as `pages[].tokenExpiresAt`. Under **7 days** left the page's token state becomes `expiring`, the flag `token_expiring:<page>` is set, and the Home status box and the admin (top of every view) print "Token for @<page> expires in <n> days — run setup-secrets or wait for the weekly refresh". A refresh that fails keeps the stored expiry and is retried next week; a code 190 during the refresh marks the token invalid and pauses the page (the hourly publisher re-probes it and resumes the page once a replaced secret works). Without `HOSHLAB_SECRETS_PAT` nothing is refreshed — a refreshed token that could not be stored would be lost — and the job only records what it knows.

**"expiry not known yet."** The tokens you paste from Meta's panel carry no expiry date, so a page whose token works (`tokenState` `ok`) but has never been refreshed is recorded with `expiresAt: null` and the sentence "expires soon" is used instead of a day count if its flag is ever raised. The first successful weekly refresh (the token must be ≥ 24 h old) sets the real expiry; from then on the day counts on the Home page and in the admin are computed from it.

## Modes

Each page has a mode in `company/config.json` (`pages[].mode`), shown as **Approve first** or **Autopilot** everywhere a human reads it. Switch it in the admin (**Modes**, typed-handle confirmation for Autopilot) or locally with `node engine/index.js set-page --page kaatdo --mode autopilot` and commit.

- **Approve first** (default for all three pages): a draft posts only when the latest `approvals.jsonl` record for it is an *approve* for its *current revision*. Approve first stops unapproved posting immediately: only drafts with an approve record for their current revision post. Drafts already in the queue wait for your approval in the admin.
- **Autopilot**: every draft that passed QA posts at its slot. Autopilot applies to drafts already in the queue: they post at their slots without an approval. Nothing posts without a QA pass; a reject on a draft still blocks it. In either mode a *reject* is final for that draft, and an *approve* made for an older revision is stale and ignored.

## How a post happens

1. **Monday 05:30 IST — CEO.** Reads the brand charters, the last 30 days of owner feedback, the latest Analyst report, the latest HR review (with the owner's decision on its proposal), this month's spend and the last 14 days of posts; writes `company/state/memos/YYYY-Www.md` (priorities per page, budget split, questions for the owner, and an **Answers to the Analyst** section with one answer per item the report filed `forCeo` — a memo that skips an item, or answers one the report does not contain, gets one repair call and is then refused, so no memo is written that week until the next run).
2. **Daily 05:30 IST — Strategist**, per page: keeps at least 2 weeks of open ideas in `ideas.jsonl` (every idea cites brand facts by id) and fills `calendar.json` for the next 14 days from the page's cadence (RishtaPatra Mon/Wed/Fri 19:30 + a Sat 19:30 reel; KaatDo Tue/Thu 08:15 + Sat 11:00 + a Sun 11:00 reel; JobRez Mon–Thu 12:30 + a Fri 12:30 reel — 13 slots a week in total), honouring `minGapHours` (6) and owner moves in `overrides.jsonl`. Reel slots exist only while `features.reels` is true (it is, since phase 2); set it to `false` and the Strategist drops them on its next run. Its prompt carries the page's feedback digest (see "How your feedback is used").
3. **Writer**: for every slot within the next 3 days (`leadDays`) without a draft, writes `drafts/<id>/draft.json` — caption (≤ 2200 code points including hashtags), ≤ 8 hashtags, alt text ≤ 100 characters, artwork text, 2–10 carousel slides or a reel of 3–6 scenes (≤ 60 characters, 3–5 whole seconds each, 15–30 s in total; style `kinetic` or `capture`), every claim tagged with the fact id it comes from. Its prompt carries the page's feedback digest too, so a reject reason you typed yesterday is in front of the Writer today.
4. **Designer** (deterministic): renders 1080×1350 JPEGs (quality 90, ≤ 1.5 MB) with Playwright Chromium from the brand's own fonts, colours and templates, refuses overflow, missing glyphs, text under the 30-unit floor or contrast under 4.5:1 (3:1 for text of 60 units and more), and writes the files to the `media` branch under `media/<draftId>/`. A feedback line tagged `design`, `variant` or `palette` that names a headline tier ("variant B") or a palette ("dark palette") steers the tier and, where a template offers both palettes, the palette; the choice and its reason land in the draft's `designNote`. A reel is rendered the same way, frame by frame (see Reels below), and encoded with ffmpeg into one silent 1080×1920 MP4 plus a poster JPEG.
5. **QA**: twelve deterministic checks (caption length, hashtags, alt text, every number traceable to a brand fact or price, forbidden words, required disclaimers, language, links on allowed domains, emoji policy, duplicates against the last 30 captions, media spec, brand lint incl. the JobRez no-country rule) and one model review; pass → `queued`, fail → back to the Writer, at most 2 loops, then `blocked` for the owner.
6. **Owner** (Approve first): approves, edits the caption, moves the slot or rejects with a reason in the admin. Every action is one commit on `main`, which also rebuilds the site.
7. **Hourly at :30 IST — Publisher** (deterministic): for each page with a usable token, takes the first queued draft whose slot has passed, checks the live Instagram quota, preflights the media URL (`raw.githubusercontent.com`, falling back to the Pages copy), creates the container(s), publishes, fetches the permalink and appends `published.jsonl`. One post per page per run. Three failed attempts → `failed`; an Instagram token error pauses that page. A draft whose slot passed more than 48 hours ago expires unpublished.
7a. **1st of the month 05:30 IST — HR** (also on demand: `node engine/index.js hr`, which forces the review of the previous month): the engine first computes every agent's numbers for the month that just ended from its own logs — calls, failed calls, cost and mean latency from `usage/YYYY-MM.jsonl`, runs and failed runs from `runs/YYYY-MM.jsonl`, failures per provider, the Writer's QA rejection rate and rework loops from the drafts written that month, and the studio's cost per approved post from `published.jsonl` — then calls the HR model once with the roster, those stats, the month's owner feedback and the enabled providers' model tables. The answer must review every agent exactly once with evidence copied verbatim from the stats ("evidence number not in stats" otherwise — one repair call, then the step fails), may change only `model`, `provider`, `temperature` (0–1) or append a paragraph to a charter, and the roster that would result is validated like any roster edit, so a proposal can never remove or disable QA or the Publisher. It writes `company/state/hr/YYYY-MM-review.md` (Markdown + a JSON block with the output and the stats) and `company/state/hr/proposals/YYYY-MM.json` with status `proposed` — HR never edits `roster.json`. The owner applies or dismisses the proposal in the admin's Roster view: **Apply** writes the proposed values into `roster.json` (re-validated in the browser) and appends `company/state/hr/decisions.jsonl`; **Dismiss** appends the decision only; the proposal file is never modified, its status on screen is derived from the decisions log. A month without runs is `skipped: no_data`; a missing proposal is caught up on the next daily run; the first review appears after one month of runs.
8. **Sunday 05:30 IST — Analyst** (also on demand: the admin's **Run analyst** or `node engine/index.js analyst`): for every published post that has been live 48 hours and 7 days and is not measured yet, one `GET /{igMediaId}/insights?metric=reach,views,likes,comments,saved,shares` → one line per post and window in `company/state/metrics/YYYY-MM.jsonl` (the month of the fetch; a metric Meta leaves out is never written as 0 — the post stays unmeasured and is retried next run). Then the weekly report `company/state/reports/YYYY-Www.md`: the model receives only the metrics records of the last 28 days plus the engine's counts and sums over them, and the engine rejects any report (one repair call, then the step fails) whose numbers are not in that set — "report number not in metrics". No post with insights yet → no report (`skipped: no_metrics`). The report lands on the site's Reports page; the first real report appears after the first Sunday with a post that has been live for 48 hours.
9. **Site**: `pages.yml` rebuilds https://sudish007.github.io/hoshlab/ from the state after every state commit — Home status, Team, per-page charters, Activity (every run, every agent step), Calendar, Published posts, Reports (one page per weekly report), feed.xml.

## Honesty rules

Enforced by code, not by promises:

- **Facts only from `brand.md`.** The Writer is offered only facts with a source pointer and status `confirmed` or `source-only`; `disputed` facts are hidden from it and from QA's number allow-list. No charter contains user counts, testimonials or ratings, so none can be written.
- **Nothing posts without QA**, and in Approve first nothing posts without the owner.
- **Costs are visible.** Every model call is one line in `company/state/usage/YYYY-MM.jsonl` with provider, model, tokens and USD from the price table in `config.json`. The month budget is USD 25 with a hard stop at 100 % (warning at 80 %): when it is spent, drafting pauses and the Home page says so.
- **Real numbers, human labels.** Every number on the site, in the admin and in this README is computed from the state files at build time or copied from `config.json`; config tokens (`approve_first`, cron strings) never appear on a public page. Anything that is not built says so: **not built yet**, **not configured yet**, **untested**.
- **Mock output is labelled.** With `MOCK_LLM=1` every usage line carries `mock: true` and every draft `mock: true`; QA fails mock drafts with `mock_output`, so a mock run can never reach Instagram. A mock Analyst report is labelled `mock: true` in its JSON block and the Reports page says "mock run"; and because the mock answer is pinned to the test fixture's numbers, a mock run against any other company state fails the number rule and writes no report.
- **Reports quote only fetched numbers.** Every number in a weekly report — in the Markdown, the per-page table and the items for the CEO — must be an Instagram insights value from `metrics/`, a count or sum the engine computed over them, a window constant (48 h, 7 d, 28 days) or a date of that week; ratios and percentages the model works out itself are rejected. The dry-run Instagram client answers zeros labelled `dryRun: true`, never a plausible-looking number.
- **Nothing confidential in the repository.** `company/` holds no keys, tokens or personal data; the repository is public (see Limits).

## How your feedback is used

Everything you type in the admin — a reject reason (**Reject with reason**) or a note (**Tell the CEO**) — is one line in `company/state/feedback.jsonl` (`{ at, by, kind: reject | note | praise, page?, draftId?, text, tags }`). The file is yours: the agents only read it. Three readers, nothing else:

- **Writer and Strategist** (`engine/lib/feedback.js`): before every call for a page, the engine builds a digest of the last 10 feedback entries addressed to that page (its own plus company-wide notes without a page), rejection reasons first, then newest first, each as `- <date> <kind>: "<text>" [tags]`, followed by the latest Analyst report's observations for that page. It is trimmed to 1,500 estimated tokens (characters ÷ 4) at a line break with a `…(truncated)` marker and placed in the prompt under **Owner feedback and observations**; when there is no feedback and no report the prompt is exactly the Phase 1 prompt. A test composes the Writer prompt from the fixture company and checks the fixture's rejection reason is in it.
- **CEO**: the memo task carries every feedback entry of the last 30 days with its tags, the latest Analyst report and the latest HR review; the charter tells it to read your feedback first and repeat your wording in `why`.
- **Designer** (deterministic, no model): only entries tagged `design`, `variant` or `palette` count, and only when the text names a tier — `variant A`, `variant B` or `variant C` (104 / 84 / 68 units; the measured tier otherwise) — or a palette — `dark palette` or `light palette`. The newest such entry for the page wins. The preferred tier is rendered first; if the copy does not fit it, the measured tier is rendered instead and `designNote` says so (`variant A preferred by owner feedback 2026-10-10 — did not fit (overflow), measured tier kept`). A palette preference applies only where a template offers both palettes — today the KaatDo carousel body slides, light unless you prefer `dark`; elsewhere `designNote` records `not offered by this template, brand palette kept`. Nothing is inferred from tone or wording: "make it bolder" steers nothing, "variant A" without a tag steers nothing.

Tags: the admin's reject dialog and note box write `tags: []` today (a tag field is **not built yet**); to tag a line, edit `company/state/feedback.jsonl` on GitHub (it is admin-owned, so the engine never overwrites your edit) and set `"tags": ["design", "variant"]` on the line. HR reads the month's feedback as strings in its review; nothing else in the company reads the file.

## Cadence

One set of strings, used identically in `company/config.json` (`schedule.*`), on the site, in this README and in the comment at the top of all five workflow files (a test checks they are byte-identical):

- Engine: **Daily 05:30 IST** (`engine-daily.yml`, cron `0 0 * * *` UTC).
- Publisher: **Hourly at :30 IST** (`publisher-hourly.yml`, cron `0 * * * *` UTC — that is :30 in IST).
- **Actions cron may start 10–30 min late**; a slot is never posted early. A 19:30 IST slot posts in the first publisher run at or after 19:30 IST — normally the 20:30 IST run, i.e. between 20:30 and about 21:00 IST. A post more than 6 hours after its slot is marked `late` in `published.jsonl` and on the Published page.
- Change the cadence in `config.json` (`pages[].cadence.slots`, ≤ 7 per page per week; formats `image`, `carousel` or `reel` — a `reel` slot is scheduled only while `features.reels` is `true`); the Strategist re-plans from the next run and drops planned slots the cadence no longer produces. Today: RishtaPatra Mon/Wed/Fri 19:30 + Sat 19:30 reel, KaatDo Tue/Thu 08:15 + Sat 11:00 + Sun 11:00 reel, JobRez Mon–Thu 12:30 + Fri 12:30 reel.

## Reels

Two styles, one pipeline, no sound. The Writer chooses the style per draft (`reel.style`) and writes 3–6 scenes of ≤ 60 characters, 3–5 whole seconds each, 15–30 s in total (`defaults.reel` in `config.json`: `minSec`, `maxSec`, `kineticScenes`, `captureScenes`).

- **`kinetic`** — kinetic typography: every scene's line types on, grapheme by grapheme, over the brand's own background (`engine/render/templates/<brand>/reel-kinetic.html`), with the brand row, a scene counter, a progress bar and the footer. The first scene is the hook and is shown in full from frame 0, because frame 0 is also the poster.
- **`capture`** — real product screen capture: Playwright records the product's **own public pages** at a 1080×1920 phone viewport (360×640 at device scale 3) — only the paths listed under `## Formats → capture:` in the brand file, each with a source pointer and a `verified <date>` stamp, only on the brand's allowed domain — and the template (`reel-capture.html`) shows them inside a phone frame with the scene text as a caption bar. Three frames per page (top, 33 %, 66 % of the scroll). Nothing is fabricated: a page that does not answer 200, times out or sits on another host is `capture_unreachable`, the draft stays `written` with that `renderError`, and the next run tries again.
- **Frames → MP4**: the template exposes `setProgress(t)`; the Designer steps it at 30 fps, screenshots `#canvas` to PNG frames and runs `ffmpeg -framerate 30 -i frame-%05d.png -c:v libx264 -profile:v high -level 4.1 -pix_fmt yuv420p -movflags +faststart -an -r 30 out.mp4`. ffprobe must then confirm `h264`, 1080×1920, `yuv420p`, `30/1`, 3–90 s, ≤ 60 MB (house cap; 100 MB is git's hard cap) and `moov` before `mdat`; the summary is recorded on the draft's video media row and QA's `media_spec` reads it back. Files are `media/<draftId>/reel-<sha8>.mp4` and `poster-<sha8>.jpg`.
- **Silent reels.** No audio track is produced or uploaded (`-an`); Instagram's acceptance of a silent reel is **untested until the first reel publish**. Captions still carry every disclaimer.
- **Locally: untested — ffmpeg not installed.** The owner's machine has no ffmpeg/ffprobe, so the reel render test skips with `skipped: ffmpeg/ffprobe not installed (runs in CI)` and a reel draft rendered locally is recorded as **untested** (`reel: untested — ffmpeg not installed`, the draft stays `written`). CI (`ci.yml`, ubuntu-latest) sets `REQUIRE_FFMPEG=1`, so there the test must run and a missing ffprobe fails the build. To test locally: `winget install Gyan.FFmpeg`, open a new shell, then `$env:RENDER_TESTS='1'; npm test`.
- **Publishing reels.** The Publisher preflights the MP4 (`HEAD` must answer `200` with `Content-Type: video/mp4`; the Pages copy is the fallback) and the poster (`image/jpeg`), creates one `REELS` container (`video_url`, `caption`, `cover_url` = the poster, `share_to_feed`), polls `GET /{container}?fields=status_code,status` every `ig.pollIntervalMs` (5 s) until `FINISHED` for at most `ig.pollMaxMs` (300 s), then publishes and fetches the permalink. `IN_PROGRESS` past the limit, `ERROR` or `EXPIRED` is one failed attempt (stage `status`, reason `timeout` / `error` / `expired`); the next hourly run creates a new container, and the third failure marks the draft `failed` like any other post. Whether `raw.githubusercontent.com` serves `.mp4` as `video/mp4` is **untested** until the phase-2 live step checks a pushed sample (Pages does serve `video/mp4`); if it does not, the preflight falls back to the Pages URL by itself. The real publish of a reel is **untested** until the owner's first one.
- `node engine/index.js render-sample --page <handle> --format reel --style kinetic` renders the page's fixture reel into `.media/media/sample-<handle>-reel/` (flagged `sample: true`); the `render_sample` input of `engine-daily.yml` does this for every page on the runner and pushes the media branch (`media: samples`).

## Limits

- **Drafts are public.** The repository is public, so unpublished drafts, QA notes, memos and rejected ideas are readable by anyone who looks at `company/state/`. The owner's approval controls what posts, not what is visible in the repository. Never write anything confidential into `company/`.
- **Schedules drift.** Actions cron may start 10–30 min late, and top-of-hour crons (all three of ours fire at :00 UTC) can be late by more than 30 minutes on busy days. A slot posts in the first publisher run at or after its time.
- **Instagram caps API publishing.** Meta's content-publishing guide states a cap of **100 API posts per 24 h** per account in one place and 50 in another; the Publisher reads the live `content_publishing_limit` (`quota_usage` / `quota_total`) before every post and stops with 2 posts of headroom, so the number is never hard-coded.
- **Tokens expire.** Long-lived Instagram tokens expire after 60 days; the weekly `token-refresh.yml` run refreshes them (see Secrets → Token refresh) as long as `HOSHLAB_SECRETS_PAT` is stored and itself unexpired, and the Home page and admin warn ("expires in <n> days") under 7 days. A token whose expiry is not known yet (never refreshed) cannot be counted down; the first successful refresh fixes that. When a token dies mid-month the publisher records `token_invalid:<page>`, the page pauses, and the Home page and admin say so; run `scripts\setup-secrets.ps1` with the new token. Every hourly publisher run then probes the paused page once with the stored secret (`GET content_publishing_limit`, no draft involved): an answer clears the pause and the page's queued drafts post in that same run; another code 190 keeps it paused. The script also resets the token state in your local `company/state/status.json` (and names the file) — that commit is optional and, because the bot rewrites `status.json` every hour, needs `git pull --ff-only` before `git add company/config.json company/state/status.json; git commit; git push`. If `git pull --ff-only` refuses because `company/state/status.json` changed upstream, run `git checkout -- company/state/status.json` and pull again; the publisher clears the pause itself on its next hourly run. The weekly refresh has run **zero times** so far (**untested** live until the first Monday after the PAT is stored).
- **The admin reads the draft index, not every draft folder.** The engine rewrites `company/state/drafts/index.json` (one entry per draft folder with its status, slot and revision) at the end of every daily and publisher run in which a draft changed; the admin reads that one file and then `draft.json` and `qa.json` only for the live drafts (two authenticated requests per live draft, six at a time — the live set is the drafts written for the next 3 days (`leadDays`) plus anything still queued, in rework or awaiting approval, whatever the folder's age), loads blocked, failed, expired and rejected drafts when you open **Blocked, failed, expired**, and a page's 30 most recent drafts when you open **Edit caption** (their captions feed the duplicate check); published drafts are never fetched. Until the first engine or publisher run after this version is deployed has written the index, the admin lists the folder and reads every draft, as it did before. Nothing archives terminal drafts yet (**not built yet**: the quarterly move of `published`, `rejected`, `blocked`, `failed` and `expired` drafts older than 90 days under `company/state/archive/drafts/` by the `retention` command): at 13 slots a week the folder grows by about 13 drafts a week — roughly 680 folders after a year — which costs the admin nothing per load but is validated by the engine at the start of every run and read by every site build, and GitHub's Contents API lists at most 1,000 entries per directory (reached after roughly 18 months), after which only the no-index fallback listing — never the index — would be truncated. Prune or move terminal drafts by hand before then if the archival is still not built.
- **Scheduled workflows stop on idle repositories.** GitHub disables scheduled workflows after 60 days without repository activity. Whether the bot's own state commits keep the repository "active" in GitHub's sense is not something this README can promise (**untested**); if the Actions page ever shows the three schedules disabled, press **Enable workflow** on each and dispatch one run.
- **One owner, one browser.** The admin is a static page talking to `api.github.com` from your browser; there are no roles, no comments or DM handling, no Stories, no paid promotion. It is tested in Chromium only (the audits); Firefox and Safari are **untested**.
- **Model and price facts age.** Model ids and prices in `config.json` were read from the providers' pages on 2026-10-10 (`pricesVerifiedAt`); `check-models` lists what each provider currently offers so the owner can correct them. Whether `gemini-3.8-flash` and `gpt-6-luna` accept the roster's `temperature` and `reasoning` settings is **untested** until the first run with real keys.

## Media retention and compaction

Rendered JPEGs and reel MP4s are committed to the orphan `media` branch (`media/<draftId>/<file>` plus `index.json`), one commit per draft, and served from `https://raw.githubusercontent.com/Sudish007/hoshlab/media/media/<draftId>/<file>` and from the site under `/hoshlab/media/<draftId>/<file>`. The fixture renders in `tests/fixtures/media/` weigh 78–119 KB per JPEG; a reel is 5–15 MB. Raw URLs point at the branch *tip*, so a file stays reachable as long as it exists at the same path on the branch.

- **Weekly retention** (`token-refresh.yml`, after the token refresh): `node engine/index.js retention --commit` deletes the MP4 of every published reel whose `publishedAt` is more than 90 days ago from the media branch (`media: retention <YYYY-MM-DD> (<n> files)`). The poster JPEG, the draft record and the `published.jsonl` line stay, so the Published page and the admin still show the reel's poster and permalink, and `index.json` keeps the entry as `{ "files": [poster], "removed": [{ "file", "removedAt" }] }`. Instagram keeps its own copy. `node engine/index.js retention --dry-run` lists what the next run would remove; `--days <n>` changes the threshold for one run.
- **Quarterly compaction** (owner-run; the deleted blobs stay in the branch's history until it is rewritten): `node scripts/compact-media.mjs --dry-run` clones the media branch into a temp folder, builds one parentless commit with the tip's exact tree and reports `<n> commits -> 1`; then `node scripts/compact-media.mjs` does the same and force-pushes **only** `refs/heads/media` with `--force-with-lease` on the sha it cloned. The script refuses `main`/`master` by name, asserts the refspec `HEAD:refs/heads/media` before pushing, and checks that `main`'s sha is identical before and after — `main` is never rewritten; this is the one place a force-push is acceptable. Afterwards refresh your local worktree with `git -C .media fetch origin media; git -C .media reset --hard origin/media` (the script prints these two lines). GitHub reclaims the unreachable objects in its own garbage-collection time, so the repository size falls later, not instantly.

## Instagram API version

`company/config.json` pins `ig.version` **v26.0** (`ig.versionSource` https://developers.facebook.com/docs/graph-api/changelog, `ig.versionVerifiedAt` 2026-10-10 — the newest version in Meta's "Available Graph API Versions" table that day; v21.0, the design's placeholder, is available until 2027-01-21). Every Instagram call uses `https://graph.instagram.com/v26.0/…`. Honest caveat: `curl -sS -i "https://graph.instagram.com/v26.0/me?fields=id,user_id,username"` without a token answers `HTTP 400` with the same `code 190` ("Invalid OAuth 2.0 Access Token") envelope as a made-up version does (the host validates the token before the version), so the version's validity rests on the changelog table, not on that probe. When Meta deprecates v26.0, change the one value and run `check-models`/a dry run.

Insights metric names (the Analyst, `engine/ig/client.js INSIGHT_METRICS`): `reach, views, likes, comments, saved, shares` — the metrics Meta's "Instagram Media Insights" reference lists for both media product types the Publisher creates, FEED (image and carousel posts) and REELS, on v26.0: https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/insights (verified 2026-10-11; the page said "Updated: Sep 11, 2026" and "The latest version is: v26.0"). `views` replaced `impressions` (deprecated for media created after 2 July 2024) and the reel-only `plays`, so one list serves every format; carousel insights are read on the album id (Meta returns none for the children). Meta also states that the data can be delayed up to 48 hours and that `reach` is an estimate — the About page says so.

### Workflows

| File | Trigger | What it does |
|---|---|---|
| `pages.yml` — Deploy to GitHub Pages | push to `main`, dispatch, `workflow_call` | checkout `main` + the `media` branch (optional until it exists), `npm ci`, `npm test`, `npm run build`, deploy `dist/`. Concurrency group `pages`. |
| `ci.yml` — CI | push, pull request, dispatch | Chromium + fonts, `RENDER_TESTS=1 npm test`, `npm run build`, both audits, `scripts/dry-run-publish.mjs`; uploads `audit-out/` as an artifact. |
| `engine-daily.yml` — Hoshlab engine (daily) | cron `0 0 * * *`, dispatch (`agents` incl. `analyst`, `page`, `dry_run`, `mock_llm`, `render_sample`) | `node engine/index.js daily --commit …`; commits as `hoshlab-bot`, pushes `media` then `main`; calls `pages.yml` when state changed. Sundays the run includes the Analyst (insights + weekly report). |
| `publisher-hourly.yml` — Hoshlab publisher (hourly) | cron `0 * * * *`, dispatch (`dry_run`) | `node engine/index.js publish --commit [--dry-run]`; deploys only when `published.jsonl`, a draft or a page's token state / status flag changed (so a page resumed by the hourly token probe reaches the Home page in that hour). |
| `token-refresh.yml` — Hoshlab token refresh (weekly) | cron `0 2 * * 1` (Mondays 07:30 IST), dispatch (`dry_run`) | `node engine/index.js refresh-tokens --commit` (needs `HOSHLAB_SECRETS_PAT` as `GH_TOKEN`), then `retention --commit` on the media checkout; deploys only when a token state, an expiry, a flag or the media branch changed. A refresh that fails (`refresh_failed` / `store_failed`) still commits its `token_expiring` / `token_invalid` flag, exits 1 so the run shows red, and retention and the deploy run anyway (`!cancelled()`), so the banner reaches Home and the admin that morning. |

The engine, publisher and token-refresh runs share the concurrency group `hoshlab-state` (never two state writers at once) and call `pages.yml` with the group `pages` on the caller side, so a deploy never overlaps a push-triggered deploy. Pushes made with `GITHUB_TOKEN` do not trigger `push` workflows, which is why the state runs deploy explicitly. Admin writes are commits on `main` (`approve: <id> (rev n)`, `reject: <id> (rev n)`, `feedback: reject <id>` / `feedback: note`, `edit: <id> (base rev n)`, `override: <id> -> <slotAt>`, `config: @<handle> -> <mode>`, `brand: <handle>`, `brand: <handle> confirm <factId>`, `charter: <agent>`, `roster: update`, `roster: apply hr proposal <month>` + `hr: apply proposal <month>` / `hr: dismiss proposal <month>` on `company/state/hr/decisions.jsonl`); each one rebuilds the site; "Run now" in the admin dispatches `engine-daily.yml` / `publisher-hourly.yml` with `dry_run: false`, and "Run analyst" dispatches `engine-daily.yml` with `agents: analyst` (the other agents are recorded `skipped: not_selected`).
